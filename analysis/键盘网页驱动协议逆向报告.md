# GANSS 官方网页驱动 (ganss.driveall.cn) 协议逆向报告（阶段 2 · 静态提取）

> 对象：`https://ganss.driveall.cn/` 前端打包 JS（layout-classic-ExAYBiru.js，888KB）
> 方法：纯静态分析，复刻 FLX3 逆向路径。素材归档 `/tmp/ganss-web/` → 建议拷入 `analysis/ganss_web/`。
> **结论：键盘 `type=1/3/13` 与宏协议全部破解，且发现了比 EXE 协议更完整的新一代固件协议（含读回通道）。**

---

## 0. 重大发现：白名单本身放行 1452:591

官方网页驱动的设备白名单（`"vid:pid:name"` 数组）**原生包含**：
- `1452:591` = 05AC:024F —— "2.4G Dongle" / "2.4G Wireless Receiver"
- 且有专门的键盘配置模块：`1452-591-GS3104T PRO.ts`、`1452-591-GS3104T-PRO 2.4G.ts`（223KB 完整配置：键位布局、fnFuncIds、灯效、宏、高级键 SOCD/MT/TGL/CB）

**"不支持该设备"报错的真正原因不是 VID 白名单**，而是更上层的按 `productName` 的
映射选择逻辑或 WebHID 授权流程差异（`collections[0].usagePage` 检查等）。
因此 WebHID hook 只需伪装极少的属性（详见 hook 脚本），协议层无需伪造报文。

## 1. 新一代协议总览（网页驱动 ↔ 新固件）

与 EXE 逆向的旧协议（04 xx 命令 + 64B feature）**并存**，网页驱动用的是 **32 字节
Output Report + AA 头**的新协议：

```
报文布局 (wn 函数逐字还原):
[0] = 0xAA                      固定头
[1] = cmd                       命令字 (见 Ge 枚举)
[2] = payload_len               本包数据长度
[3] = addr & 0xFF               地址低字节 (分块偏移)
[4] = addr >> 8 & 0xFF          地址高字节
[5..7] = otherHeader 前3字节    (可选)
[6] = 0/1 last-packet flag      (无 otherHeader 时)
[8..31] = data                  24 字节有效负载 (headerCount=8)
```

- 分块：`chunk = 32 - headerCount(8) = 24` 字节/包，`SET_KEY` 等大表按地址递增分块
- 响应匹配：inputreport 按 command 过滤（`no(e,{command,timeout,addr},...)`）
- 音乐数据等自定义包：`g[31] = sum(g[0..30]) & 255` 校验
- `sendReport(So=reportId 0, ...)` — 无 Report ID 模型，与 EXE 通道一致

### Ge 命令枚举（完整提取，88 条）

```
COMMUNICATION_START=1  COMMUNICATION_END=2  SET_FACTORY_RESET=15
GET_DEVICE_INFO=16     GET_KEY=18           GET_LED_EFFECT=19
GET_MACRO=21           GET_FN_KEY=22        GET_DEFAULT_FN_KEY_MATRIX=28
GET_DEFAULT_KEY_MATRIX=31

SET_KEYBOARD_CUSTOM_FUNCTION_ON=48 / OFF=49     ← 驱动自定义开关可软件切换!
GET_LED_DATA=50        GET_ALL_LIGHTS_RGB=51
GET_ALL_LIGHTS_RGB_24G=55 / _64_BYTE=59

```

**关键**：`SET_KEYBOARD_CUSTOM_FUNCTION_ON/OFF (48/49)` —— 说明新固件可以直接
软件开启驱动自定义模式，**无需 Fn+Tab**！另 GET_KEY/GET_DEFAULT_KEY_MATRIX
证明**键位表可以硬件回读**（推翻阶段 0 "键位层无回读" 的结论，仅适用于旧固件）。

## 2. 键位记录编码（Rs 编码器 + to 解码器，逐字还原）

每键 4 字节记录，与 EXE 协议的 `[type,mask,usage,0]` **不同**（新协议布局）：

| page | type | 字节布局 | 说明 |
|---|---|---|---|
| DEFAULT | 0 | 全零 | 默认 |
| MOUSE | 1 | `[1, param1, value, 0]` | param1=1 点击/3 滚动；value: 1左 2右 4中 8后退 16前进，滚动 1上 255下 |
| KEYBOARD | 2 | `[2, param1(修饰), usage, 0]` | param1: LCtrl1/LShift2/LAlt4/LWin8/RCtrl16/RShift32/RAlt64/RWin128 —— **修饰键在字节1，usage 在字节2**（与 EXE 相反顺序!） |
| CONSUMER_KEY | 3 | `[3, usage&255, usage>>8, 0]` | **Consumer Page 16-bit LE，与 FLX3 一致** |
| MACRO | 6 | `[6, macroId, param2, param3]` | 宏引用 |
| CB | 7 | `[7, p1, p2, p3]` | 组合触发 |
| DKS | 8 | `[8, value]` | 磁轴 |
| TGL | 10 | `[10, value]` | 切换 |
| FUNC | 13 | `[13, v>>16, v>>8, v&255]` | 旧功能 |
| FUNC_V2 | 128+ | `[(128\|l>>8&127), l&255, r>>8, r&255]` | 新功能 |
| END | 14 | `[14, p1, p2]` | 结束 |

**修饰键语义已解**：键盘 type=13 并非媒体键；媒体键是 **type=3 (CONSUMER_KEY)**。
EXE 协议的 type=13 对应新协议 FUNC；type=1 (MOUSE) 同样存在。

### Consumer Page 键码表（完整提取，与 FLX3 完全一致）

## 3. 宏协议（完整闭环，含读回）

### 内存布局
- **宏指针表**：400 字节 @ addr 0，每宏 4 字节 LE32 偏移（0=空），最多 100 个宏
- **宏数据块** @ addr 400 起，每块：`[u16 LE 字节数(=事件数*2), 0, 0, 事件×4B]`

### 事件 4 字节编码（fd 序列化器逐字还原）
```
[b0] = delay & 255          延迟低字节
[b1] = delay >> 8           延迟高字节 (16-bit LE, ms)
[b2] = keyCode              usage/键码
[b3] = flags: 
       actionType 1/2 → isPress? 0x90 : 0x10   (144/16)
       其他        → isPress? 0xB0 : 0x30   (176/48)
```
读取侧解码：`isPress = b3 & 128`，`actionType = b3>>4 & 7`，`delay = b0|b1<<8`。
**注意 delay 是"事件前延迟"**（录制时为按键间隔），与 FLX3 的"事件后延迟"字段位置不同。

### 下发流程 (SET_MACRO=37)
1. `ra(cmd=37, contentSize=400, addrStart=0, isNeedLastPacketFlag=false, data=指针表)`
2. `ra(cmd=37, contentSize=总数据, addrStart=400, isNeedLastPacketFlag=true, data=宏块拼接)`

### 读回流程 (GET_MACRO=21)
1. 读指针表 400B → 解析每宏偏移
2. 每宏：读 4B 头得事件数（字节数/2/2），再读 `事件数*4` 字节

## 4. 键位表协议（新固件）

- 普通层：`SET_KEY=34`，128 键 × 4B = 512B，分块（24B/包）下发
- Fn 层：`SET_FN_KEY=38`，同样 512B 结构
- 读回：`GET_DEFAULT_KEY_MATRIX=31` / `GET_DEFAULT_FN_KEY_MATRIX=28`（出厂默认）
- 当前层读回：GET_KEY=18
- 滚轮键：普通层表尾部附加（GS3104T PRO 无滚轮则全零）

## 5. 灯光协议（16 字节参数块）

```
GET_LED_EFFECT=19 读 / SET_LED_EFFECT=35 写, 16B:
[0]=mode [1..3]=RGB [4]=255 [5..7]=secondaryRGB [8]=colorMode
[9]=brightness [10]=speed [11]=direction [12]=effectModeType
[14]=0xAA [15]=0x55
```

## 6. 设备信息（GET_DEVICE_INFO=16，48B）—— 插件 probe 用

```
[0] romSize [2..3] macroSpaceSize [4..5] vid LE [6..7] pid LE
[8..9] version BCD-ish [10..11] sensor [12..15] manufacturer/product str idx
[16] workMode [17] batteryLevel [18] chargeStatus [19] currentProfile
[30] frameVersion [31] lightingVersion [32] firmwareStatus
```
含**电量读取**（batteryLevel/chargeStatus）——键盘认知再升级：老固件无此通道，
新固件有完整遥测。

## 7. 双协议适配结论

| 项 | EXE 老协议（已实机验证） | Web 新协议（静态提取，待实机） |
|---|---|---|
| 载体 | 65B feature (04 xx) / 33B 短报文 | 32B output report (AA 头) |
| 命令 | 04 11/13/15/17/27/F0 | Ge 枚举 88 条 |
| 键位记录 | [type,mask,usage,0]（mask 在前） | [type,modifier,usage,0]（modifier 同位,usage 后移1）|
| 媒体键 | type 1/3/13 语义未解 | **type=3 CONSUMER_KEY 16-bit LE** |
| 宏 | 04 15/19 未解码 | **完整指针表+事件块+读回** |
| 键位回读 | 无 | GET_KEY/GET_DEFAULT_KEY_MATRIX |
| 自定义开关 | Fn+Tab 手动 | SET_KEYBOARD_CUSTOM_FUNCTION_ON/OFF |
| 电量 | 无 | GET_DEVICE_INFO [17] |

**策略**：现有插件保留 EXE 协议（已实机验证）作为**稳定通道**；新增 `web_protocol.py`
实现新协议作为**增强通道**（探测 GET_DEVICE_INFO 成功即启用），逐步切换：
媒体键/宏/键位回读/电量走新协议，基础灯光/单键映射先保持旧协议。
